# サブエージェントのプロファイル（モデル）選択

- **対象**: `src/agents.rs`（`AgentMeta` / `AgentDef` のフロントマター）、
  `src/tools/subagent.rs`（`run_and_store` のプロバイダ解決）、
  `src/config.rs`（定義の検証）、`src/main.rs`（登録時の検証）、README
- **前提**: サブエージェント本体（#202 系の2026-09-02仕様）と
  `ProviderRegistry` のプロファイル解決・`fallback_provider` がマージ済み

## なぜ

初回仕様の「やらないこと」に明記されていた **エージェントごとのモデル選択を、
今回はいれる**。動機は2つ。

**メインはローカル、サブは外部。** メインエージェントは日常会話用につき、
気軽に話したい・内密にしたい話もあるので費用のかからないローカルモデルで
動かしたい。一方開発の本格的な作業（実装・レビュー）をローカルモデルで
こなすのはスピードが心もとない。サブエージェントはすでに「メインの文脈を
持ち込まない専門実行環境」として設計されているのだから、
**モデルの専門特化も定義の一部に乗せるのが筋が通る** —
ツール一覧の制限（`tools:`）と同じ位置づけである。

**プロンプトキャッシュの問題は構造的にはすでに解れている。** サブエージェントは
独立したネスト会話でシステムプロンプトも独立（初回仕様の決定2）なので、
メイン側のプロンプトキャッシュを蹴らすのはローカルLLM（llama.cpp）側で
メインとサブが同じKVキャッシュを共有してしまう問題に限られる。
サブを別プロバイダ（別プロセスの外部API）に振れば、これは設定ではなく
構造の話として解消する。

## 決めたこと

### 1. 指定は定義のフロントマター `profile:` のみ

`<workspace>/agents/<name>.md` のフロントマターに `profile` を1つ足す。
それがすべて。全局デフォルト（`[tools] subagent_profile` 等）は**入れない** —
「サブは全部このモデル」は `[profiles.<name>].provider` を生やす側で
どうにでもなるし、未指定時は親追従（次項）のほうが常に正しい既定値だから。

```markdown
---
description: コードレビュー。差分を読んで問題を報告する。編集はしない。
tools: [client_file_read, workspace_search, retrieve]
profile: dev
---
あなたはレビュアーです。…
```

- `profile` を**省略した定義は現状どおり親（主エージェント）のプロバイダを
  使う**。既定の動作は一切変わらない。
- `profile` を**指定した定義は、その `[profiles.<name>]` を通じて解決された
  プロバイダで走る**。`ProfileConfig` は `provider` と `fallback_provider`
  の両方を見るので、既存の拒否反応フォールバック機構がサブにもそのまま
  効く。将来のオフライン時ローカルフォールバックも、この `fallback_provider`
  の仕組みで表現できる — サブ固有のフォールバック機構は新しく作らない。
- `AgentMeta` / `AgentDef` に `profile: Option<String>` を1本足すだけの
  変更で、解決経路は `provider_for_session` と同じ
  `ProviderRegistry::for_profile` をそのまま使う（プロファイル解決の
  意味論を2系統にしない）。

### 2. 未指定時の挙動は「サーバーは落としてよい、クライアントは落とさない」でおく

未指定時の挙動変更を求められているのは、将来 sapphire-agent が
ledger / journal と同じくリモートワークスペース同期＋ローカルループ構成に
なったとき、**同期された設定がローカル環境で成立しない**ケース
（ローカルから到達できないプロバイダ名が書いてある）が起きうるからだ。
しかしそのときでも壊れるのは「名前解決」ではなく「到達可能性」のはずで、
後者はすでに `fallback_provider` が面倒を見る。

したがって方針を2層に分けておく:

- **名前解決（この仕様）** — `profile:` に未知の名前が書かれていた場合、
  サーバー構成は**起動時に検証エラーで落とす**。設定ファイル内の静的な
  参照ミス（タイプミスしたプロファイル名で静かに別モデルへ流れる）は
  静かに黙らせるより落としたほうが被害が小さい。これは既存の
  `Config::validate_profiles` が設定読み込み時にエラーで落としているのと
  同じ方針で、方針として統一する。
- **到達可能性フォールバック（将来）** — リモート同期＋ローカルフォールバック
  構成では、未知の名前を警告して親プロバイダへフォールバック、に
  挙動を変えうる。そのために**解決の入口を `for_profile` 単一関数に
  集約しておき、「名前が引けないときの扱い」だけを差し替え可能な1点に
  固めておく**。今はそこに起動時検証（強制）を被せるだけで、
  将来の挙動変更は設定の追加ではなくその1点のポリシー変更で済む。

### 3. 検証の位置

`load_agents_dir` は現状「1つ壊れていても他は動かす」方針で、壊れた定義は
警告して飛ばす。しかし **未知の `profile` 参照だけはこの方針を変えて
起動時エラーにする**（前項）。ローディングを宽松に保ったまま検証だけ厳しく
するため、チェックは `load_agents_dir` の内側ではなく、`main.rs` が
エージェント定義と設定の両方を持って登録する時点で走らせる:

- 読み込み: 従来どおり壊れた YAML は警告してスキップ
- 検証: 読み込みに成功した定義群の `profile` 値を `config.profiles` と
  突き合わせ、未知の名前があれば**起動を失敗させる**（エラーメッセージは
  `validate_profiles` と同様に全件列挙）

エージェント定義が1つも無いデプロイでは検証も何もしない（従来どおり
ツール自体を登録しない）。

### 4. resume は無条件に復活する

`subagent_cache` に保存されるのはプレーンな `ChatMessage` 履歴だけで、
プロバイダ依存の表現（ツール_useブロックの内部形式等）は保存されない。
よって**ハンドル生成後に定義の `profile:` を書き換えても、既存ハンドルの
resume は新しいプロバイダでそのまま成功する** — 履歴の書式がモデル非依存に
なっていることによる自然な帰結であり、仕様として明記して回帰テストも
ここに置く。

### 5. 実行時に何も変えない

プロバイダの選択が `ctx.provider` 直参照から
「定義に `profile` があれば `ctx.state` 経由で解決、なければ `ctx.provider`」
になるだけで、TurnLoop に渡すものも、`SubagentHost` が親のホストであることも、
ツール一覧のゲート（`NotOffered`）も深さ1の再帰制限も、何も変わらない。
サブエージェントのツール呼び出しは引き続き**親と同じゲートを親の `Origin` で**
通る — サブが別プロバイダのモデルで動くことは許可ゲートに何も影響しない。

## データフロー

```
親のモデルが subagent{agent: "implementer", prompt: "…"} を呼ぶ
  → 許可ゲート（従来どおり、親の Origin）
  → 定義を引く
     profile なし  → プロバイダ = 親と同じ（従来どおり）
     profile あり  → ctx.state.registry.for_profile(config, name)
                     （未知の名前は起動時に弾かれているのでここに届かない）
  → 以下従来どおり（ネストループ、非永続化、親の TurnHost）
```

## エラー処理

- **`profile:` が未知の名前**: 起動時に検証エラーで落とす（決定2・3）。
  実行時に unknown に会う経路は存在しない。
- **プロバイダは解決できたが疎通できない**（API障害・オフライン）:
  既存のプロバイダ呼び出し失敗と同じ — エラーをツール結果に返し、親のターンは
  落とさない。`fallback_provider` が設定済みならその手前で吸収される。
- 定義のフロントマターが壊れている／`description` が無い、は従来どおり
  警告してスキップ。

## テスト

- `profile:` 付き定義が、そのプロファイルのプロバイダで走る
  （プロバイダを差し替えてサブのターンが走ることを既存のテスト用
  provider ダブリンで確かめる）
- `profile:` なし定義が従来どおり親のプロバイダで走る
- 未知の `profile` を持つ定義で `main` 相当の検証が失敗し、
  エラーメッセージに全件が含まれる
- 壊れた定義はスキップ、`profile:` 検証は通る（スキップされた定義は
  検証にも現れない）
- 定義の `profile` を起動後に変更した resume が新プロバイダで成功する
- 既存のサブエージェントテスト（system prompt 継承なし、`subagent` 再帰禁止、
  ゲート共通）が全てそのまま通る

## やらないこと

- **全局デフォルトのプロファイル**（`[tools] subagent_profile` 等）。未指定時
  親追従で十分なため入れない。
- **エージェントごとのツールラウンド予算・思考量などのプロバイダ以外の上書き**。
  今回 `profile` 以外にフロントマターへ入れるものは無い。
- **リモートワークスペース同期＋ローカルフォールバック本体**。
  リモートワークスペース機能側に寄る将来仕様で、ここでは決定2の
  「解決入口を集約しておく」準備だけ入れておく。
- **定義のホットリロード**。プロファイル参照の検証も起動時に1度きり
  （heartbeat タスクと同じ）。
