# システムプロンプトのピン留め — 編集でプロンプトキャッシュを壊さない

- **対象**: `server/src/workspace.rs`（`Workspace::read_file` / `build_system_prompt` / 生ログ・ダイジェスト読み込み）、
  `server/src/agent.rs`（`SystemSnapshot` / `invalidate_system_prompts`）、`server/src/serve/mod.rs`（`run_llm_turn` のシステムプロンプト生成）、
  `server/src/heartbeat.rs`（デイリーログ生成後の無効化呼び出し）、`server/src/tools/`（新ツール `refresh_system_prompt`）
- **前提**: プロンプトキャッシュ（provider 側の prefix キャッシュ）は、システムプロンプトのバイト列が前回と一致したときだけ効く。
  すでに「クロックをプロンプト入れずに `current_time` ツールへ移した」対策（workspace.rs のコメント参照）が入っているのは同じ理由。

## なぜ

システムプロンプトは AGENTS.md / SOUL.md / IDENTITY.md / USER.md / TOOLS.md / BOOTSTRAP.md ＋ MEMORY.md（名前空間チェーン）＋ 昨日のデイリーログ＋週次/月次/年次ダイジェストを連結したもので、全セッションの全リクエストの先頭に付く。プロンプトキャッシュはこのプレフィックスが**1バイトでも違えば**全リクエストでキャッシュが壊れ、システムプロンプト＋ツールリザルトを乗せた履歴全体を再処理させる。

現在の読み込みは「編集即反映」の2段構えになっている:

1. **層1（共通・根本原因）** `Workspace::read_file` が **mtime キャッシュ**を持つ。
   `CachedFile { content, mtime }` をパスごとに保持し、mtime が変わると即座に再読込して新内容を返す。
   → SOUL.md を1行直すだけで、次の読み込みから全パスのプロンプトが変わり、キャッシュが壊れる。
2. **層2（チャネルパスのみ）** `agent.rs` の `get_system_prompt` は会話キー（`ConversationKey`）ごとに
   `SystemSnapshot { system_prompt, date }` をキャッシュし、**ローカル日付（day_boundary_hour 基準）が変わるまで**
   スナップショットを再利用する。無効化は `invalidate_system_prompts()`（スナップショット全消去）だけで、
   呼び出し元は `heartbeat.rs` のデイリーログ/ダイジェスト生成後のみ。→ チャネル側は実装済み設計に近い。
3. **ACP/デバイスパス**（`serve/mod.rs` の `run_llm_turn`）は層2に相当するスナップショットを持たず、
   **毎ターン `build_system_prompt` を呼んで disk を再読込**する。→ 層1を直さないと毎ターン露呈する。

## 仕様

### 核心的不変条件（実装前に理解すべきこと）

**ピン留め後は、実効的にプロンプトの内容が変わるのは (a) デイリーログ等生成後の無効化と (b) `refresh_system_prompt`
ツール呼び出しの2瞬間だけ**である。日境界そのものはピン留めを解かない——日境界でスナップショットが再生成されても、
ピン留めキャッシュが同じ内容のままなら生成されるバイト列は前回と同一であり、プロンプトキャッシュは壊れない
（＝日境界単独では何も変わらない。リフレッシュの実体は常に (a)/(b) の無効化である）。
無効化は必ず「デイリーログ等の生成が完了した後」に呼ぶこと（heartbeat.rs は生成完了後に呼ぶ順序を維持）。

### 1. `Workspace::read_file` を mtime 即反映 → ピン留めに変更

- mtime を**無視**し、パスごとに一度読んだコンテンツを以降ずっと返す（＝ピン留め）。
- 再読込は**キャッシュ明示クリアのときだけ**行う。
  - 実装: `CachedFile { content, mtime }` を `content: String` のみに変えるか、mtime を残して「クリア時のみ上書き更新」にする。
- **存在しないファイルも状態としてキャッシュに保持する**（欠落マーカー的に `Option<String>` 値で保持）。
  現行のような「存在しないならキャッシュ除去」にすると、毎リクエストの存在チェックが実質再読込になり、
  ピン留めの意図と矛盾するため。→ 新規作成ファイル（前日中に存在しなかった昨日分のデイリーログ等）は、
  **無効化＝全クリア後の再構築でのみ**見えるようになる。無効化は生成**後**に走るため、日境界のデイリーログ
  新規作成は正しく反映される。
- `build_system_prompt` / `build_memory_block` / `inject_periodic_logs`（デイリーログ本文・各種ダイジェスト）は
  いずれもこのピン留め読み込み経由にする。`periodic_log::read_body` / `read_digest_top_n` の直接
  `std::fs::read_to_string` 呼び出しも、**同一の `Workspace` ピン留めキャッシュ経由に置き換える**
  （別マップを持たせない。無効化時の「全クリア」が1箇所で済むようにする）。

### 2. 無効化は「デイリーログ生成後」と「明示ツール」の2経路のみ

- **`invalidate_system_prompts()`（既存）の拡張**: ①Workspace のピン留めファイルキャッシュ全クリア ＋ ②全
  `SystemSnapshot` の消去、の両方を行う。呼び出し順序は必ず「デイリーログ等の生成完了 → 無効化」。
  `heartbeat.rs` はデイリー/週次/月次/年次ログを1つでも生成したときだけこれを呼ぶ（現状の呼び出し条件を維持）。
- **新ツール `refresh_system_prompt`**: 引数なし。呼ぶと **`invalidate_system_prompts()` と同一の効果**を持つ
  （＝Workspace キャッシュ全クリアとスナップショット全消去の両方）。実装は Agent 側の無効化関数をそのまま呼ぶ形にする。
  戻り値は成功を簡潔に伝えるテキスト（例:「システムプロンプトの読み込みキャッシュをクリアしました」）。
  失敗ケースは想定しない（常時成功）。
- 結果としてチャネルパスの無効化契機は「日境界 or ツール呼び出し」の2つに限定される。

### 3. チャネルパス（agent.rs）

- `SystemSnapshot` の「日付が変わったら再構築」は**維持**（日境界でスナップショットを作り直す挙動は変えない。
  ただし上記不変条件により、ピン留めが効いている限り再構築結果は前回と同一バイト列になる）。
- `invalidate_system_prompts()` は §2 のとおり、スナップショット全消去に加え Workspace のピン留めキャッシュもクリアする
  （agent が保持する `Arc<Workspace>` 経由でよい）。

### 4. ACP/デバイスパス（serve/mod.rs）

- `run_llm_turn` は毎ターン `build_system_prompt` を呼ぶが、層1がピン留めになるので**ディスク再読込は起きず、
  バイト列は前ターンと同一**。追加実装は不要（ピン留めが効けば ACP も自動的に安定）。
  実装確認として「ファイル編集後もピン留めクリアまで同一バイト列」であることをテストで担保する。

### 前提として成立させていること（実装で崩さないこと）

- `Workspace` は**プロセスあたり単一インスタンス**で、agent.rs の `Arc<Workspace>` と serve 側が同一インスタンスを
  共有していること（現状共有されている。崩れたら §4 の「追加実装不要」が成立しなくなる）。
- キャッシュの寿命＝プロセス寿命。プロセス再起動時はピンが冷え、その時点のディスク内容が新しい基準になる
  （＝再起動をまたぐとプロンプトキャッシュは1回壊れる。これは受け入れる）。
- 複数プロセス展開は対象外。
- **クリアはアトミックな差し替えにする**（`Mutex<HashMap>` の丸ごと交換等）。クリアと再ピン留めの合間に
  別セッションのプロンプト構築が割り込んでも、「ファイル間で新旧混在した状態」で読み直すことは許容するが、
 HashMap の部分破損（ロックなしの途中状態参照）は起きないこと。

### 5. ドキュメント

- `templates/workspace/AGENTS.md`（このリポジトリのテンプレート。実ユーザー側の同ファイルは対象外でよい）に、
  メモリファイルの編集は即時反映されない（デイリーログ生成時または `refresh_system_prompt` で反映）ことを1行追記。

## 受け入れ条件

1. SOUL.md 等を編集しても、無効化（`refresh_system_prompt` 呼び出し、またはデイリーログ生成後の `invalidate_system_prompts()`）が
   走るまで、`build_system_prompt` の出力バイト列は不変。日境界を跨いだけでもピン留め中ならバイト列は変わらない。
2. 無効化後、次回のプロンプト構築は編集後の内容を反映する。デイリーログ生成→無効化の順序で、生成されたばかりの
   日次ログが次の構築から反映される。
3. 新ツール `refresh_system_prompt` がツール一覧に表示され、呼び出しでスナップショットとファイルキャッシュの両方がクリアされる。
4. 既存テスト `the_system_prompt_is_byte_identical_across_turns` はそのままパスし、
   「ピン留め中にファイル編集があってもバイト列同一」を担保する新テストがパスする。

## 非目標

- プロンプト生成ロジックそのもの（連結順・見出し・切り詰め `MAX_FILE_CHARS`）の変更。
- 日境界リフレッシュの仕様変更（既存の「日付変更でスナップショットを作り直す」挙動は維持）。
- ACP パスへのスナップショット機構の新設（層1のピン留めで十分なので作らない）。
