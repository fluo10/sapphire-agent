# ACP セッションのツール呼び出しを永続化し、ツール出力に上限を掛ける

- **対象**: `src/serve/mod.rs`（`run_llm_turn`）、`src/acp_session.rs`、
  `src/tools/mod.rs`、`src/tools/builtin_tools.rs`
- **イシュー**: [#191](https://github.com/fluo10/sapphire-agent/issues/191)
- **前提**: ACP ストア分離（PR #188）がマージ済み、または同じブランチ上

## なぜ

理由は2つあり、後者のほうが重い。

**再読み込みで「何をしたか」が失われる。** ACP セッションを開き直すと、話した内容は
戻るが、エージェントがどのファイルを読み、どのテストを走らせ、何を編集したかは
残っていない。`run_llm_turn` は `tool_use` と `tool_result` をどのトランスポートでも
捨てているので、復元された履歴は API 的には妥当だが薄い。ストア分離の spec は
これを決定4で明示していたのに、実装計画がタスクを持たなかった。結果として
`ToolResultCache` は本番の呼び出し元を持たないまま出荷されている。

**ツール結果がメモリに残り続ける。** `state.sessions` は一度も掃除されず、
`remove` も `retain` も無い。プロセスが起動中に開いたセッションは、全履歴を
抱えたまま残る。そしてツール結果には上限が無い — `truncate_output`（50 000バイト）は
シェルの stdout/stderr にしか掛かっておらず、`file_read` は読んだファイルを
まるごと履歴に載せる。エージェントが1日読んだもの全部が常駐する。

**まだ観測はされていない。** これは理屈上の圧力であって、測った結果ではない。

## メモリ問題に対して、この spec が実際にやること

正直に切り分けておく。**永続化そのものはメモリを1バイトも減らさない。**
減らすのは次の2つで、前者だけが今回の範囲にある。

- **上限（今回）**: 全ツール結果を50 000バイトに切り詰める。1件あたりの常駐量が
  縛られ、巨大なファイルを不意に読んだときの跳ね上がりが消える。
- **アイドルセッションの破棄（将来）**: `state.sessions` から落とす。
  母数そのものを縛る、おそらく一番効く手。**ストア分離によって初めて安全になった** —
  以前は捨てると会話が失われた。永続化はこれを可能にするための土台であって、
  それ自体が対策ではない。

### ターン間の参照化はしない

当初は `image_cache` に倣い、ターン終了後に `ContentPart::ToolResult` を
参照に置き換え、プロバイダ呼び出し直前にキャッシュから戻す案だった。**取り下げる。**

アイドルセッションを落とす前提に立つと、`state.sessions` に残るのは
アクティブなセッションだけになる。アクティブなセッションは定義上次のターンが来るので、
参照化した端から実体化し直す。**ピーク消費量は変わらず、毎ターンの読み直しだけが
残る。** 本番サーバーは Ceph 上で動いており、ファイルシステムの I/O は
無視できるコストではない。

上限を掛けることで、参照化が防ごうとしていた「不意の巨大化」も同時に塞がる。

これにより `ContentPart` に新しい variant を足す必要も消え、変更範囲が
永続化と上限だけに縮む。

## やらないこと

**アイドルセッションの破棄は別に設計する。** いつ捨てるか、進行中のターンをどう扱うか、
開き直しにいくらかかるか — どれも新しい方針が要る。観測がない段階で一緒に決めるのは
投機。**代わりに測れるようにする**（後述）。**参照化を取り下げた以上、これが
メモリ側の唯一の残る手**なので、測定の価値は上がっている。

**既存4ストア（`channel` / `cross-device` / `device-default` / `mcp`）の
永続化はしない。** Discord や Matrix から指示してツールを使うのは普通の使い方なので、
そこでも結果を復元できるに越したことはない。ただし安くない —
`SessionStore` にキャッシュのハンドルを通し、`ContentPart::ToolResultRef` を足し、
消費者の異なる4つの読み出し経路それぞれで復元の可否を決める必要がある
（うち `sessions_for_day_filtered` はテキストのみを保つ必要がある）。
生のまま書くのは論外で、ワークスペースと retrieve 索引が汚れる。

そして `SessionStore::append` と `load_all` は `channel` ストアの常用経路であり、
Matrix と Discord が毎日通る。**このリポジトリで一番危険な編集**で、動機の異なる
ACP の作業に相乗りさせるより、独自の spec とレビューを持つべき。
[#194](https://github.com/fluo10/sapphire-agent/issues/194) に切り出した。

**replay でツール呼び出しをエディタに出すのもしない。**
[#192](https://github.com/fluo10/sapphire-agent/issues/192) に切り出した。動機は
メモリであって、replay の描画は直交する。ただし非対称は残る: モデルは全履歴を
見るのに、開き直したスレッドではツール呼び出しの箇所が空く。今と同じ状態が続くだけで、
悪化はしない。

## 決めたこと

### 1. ツール出力の上限を全ツールに掛ける

`truncate_output`（50 000バイト、先頭20 000 + 末尾30 000、間に省略マーカー）は今
シェルの stdout/stderr にしか掛かっていない。**これを `ToolSet::execute`
（`src/tools/mod.rs:125`）に移し、全ツールの結果に掛ける。**

そこが唯一の合流点である。組み込みツールも MCP ツールも、拒否されたときの
理由文字列も、すべて `ToolOutput` としてそこを通る。ツールごとに掛けると
新しいツールが追加されるたびに掛け忘れが起きる。

シェル側の既存の呼び出しは削る — 二重に掛けると省略マーカーが入れ子になる。

理由は3つ。**メモリの常駐量が1件あたりで縛られる** — これが参照化を取り下げた後も
残る、唯一の直接的なメモリ対策。キャッシュとディスクの成長が縛られる。
ライブと再読み込みで見えるものが一致する。

そして既存の不整合が消える — なぜシェルだけ切って `file_read` は切らないのか、
という問いに答えが無かった。100MB のファイルを1回読めば、それが履歴に載り、
モデルへ送られ、ディスクに書かれる。

**代案を却下した理由。** 「無制限のまま、キャッシュを年齢で刈る」も考えた。
しかしそれは巨大な結果がメモリとモデル入力に載ることを何ら防がず、防ぐのは
ディスクの成長だけ。上限のほうが、3つとも同時に縛れる。

50 000バイトという値は既存の `truncate_output` のもので、変えない。先頭20 000 +
末尾30 000 は、ファイルの冒頭とエラーが出がちな末尾の両方を残す配分。

### 2. ACP セッションの `tool_use` / `tool_result` を永続化する

`run_llm_turn` の2箇所、今「意図的に永続化しない」とコメントされている地点で、
`is_acp` のときだけストアに追記する。

- `tool_use` を持つアシスタントメッセージ（`src/serve/mod.rs:2230` 付近）
- ツール結果のメッセージ（`src/serve/mod.rs:2336` 付近）

ストア側は既にある。`store_part` は `ContentPart::ToolUse` を
`StoredPart::ToolUse` に、`ContentPart::ToolResult` をキャッシュ書き込み +
`StoredPart::ToolResultRef` に変換する。

### 3. キャッシュ不在時に対を壊さない

現状の穴: キャッシュが無いと `store_part` は `StoredPart::Other` を書き、
`tool_use_id` を落とす。`load_part` はそれをただのテキストマーカーとして読み戻すので、
**`tool_use` に対応する `tool_result` が無い履歴ができ、API がそれを拒否する。**
書き込み側のミスは、読み出し側のミスと違って対を保てていない。

`StoredPart::ToolResultRef` の `sha256` を `Option<String>` にする。

```jsonc
{"tool_result_ref": {"tool_use_id": "c1", "sha256": "ab12…"}}   // 内容あり
{"tool_result_ref": {"tool_use_id": "c1", "sha256": null}}       // 内容なし
```

`None` は「ここに結果があったことは分かるが、中身は持っていない」。`load_part` は
どちらの場合も `ContentPart::ToolResult` を作り、内容はキャッシュから、
取れなければ `MISSING_RESULT` を入れる。**`tool_use_id` はどちらの経路でも保たれる。**

これは書き込み時にキャッシュが無い場合と、書けたが後で消えた場合を、読み手にとって
同じ形にする。読み手が区別する理由は無い — どちらも「対はある、中身は無い」。

### 4. 測れるようにする

破棄を投機で入れない代わりに、次に決めるときの材料を出す。参照化を取り下げた以上、
破棄がメモリ側の唯一の残る手なので、この測定がその判断の唯一の入力になる。

`state.sessions` の常駐量を定期的にログに出す: セッション数、メッセージ総数、
`ContentPart::Text` と `ContentPart::ToolResult` の合計バイト数、そして
最大のセッション1本の内訳。既存の30分ダイジェスト掃き出しのタスクに相乗りさせる
（別のタイマーを増やさない）。`debug` レベル。

最大の1本を出すのは、「多数のセッションが溜まる」のか「1本が長く伸びる」のかが
それで分かるため。前者なら破棄が効き、後者なら破棄は効かず別の手が要る。
合計だけでは区別がつかない。

## データフロー

```
ツール実行
  → truncate_output（ToolSet::execute、全ツール、50 000バイト）
  → ContentPart::ToolResult
       ├─ そのまま history に積まれ、そのままモデルへ渡り、
       │  そのまま state.sessions に残る（ライブの間は何も変わらない）
       └─ ACP セッションなら store へ:
            store_part がキャッシュに内容を書き、
            StoredPart::ToolResultRef{tool_use_id, sha256: Option} を JSONL へ
       ↓ 再読み込み
     history() が JSONL から組み立て直す:
       sha256 があればキャッシュから内容を、
       無ければ / ミスなら MISSING_RESULT を入れる。
       tool_use_id はどちらの経路でも保たれる。
```

**ライブのターン中、メモリ上の履歴は一切加工されない。** 加工が入るのは
ストアへの書き込み経路だけ。参照化を取り下げたので、`state.sessions` に入るものと
モデルが見るものは常に同じ。

## エラー処理

- **キャッシュ書き込み失敗**: 警告し、`sha256: None` として追記する。
  ライブのターンは影響を受けない（メモリ上の内容はそのまま）。
  再読み込みでその1件が `MISSING_RESULT` になるだけ。
- **キャッシュ読み出しミス**: `MISSING_RESULT`。対は保たれ、モデルは必要なら
  ツールを呼び直せる。
- **ストア追記失敗**: 警告して続行。今の挙動と同じ。ターンは進み、
  次の再読み込みでその部分が欠ける。
- **キャッシュ自体が開けない**: 永続化は全件 `sha256: None` になる。
  「対はあった、中身は無い」という記録は残るので、履歴は API 的に妥当なまま。

## テスト

- ツール結果が JSONL に参照として書かれ、内容は JSONL に現れない
- `tool_use` と `tool_result` の対が、キャッシュを消しても保たれる
- **キャッシュ不在で書いた結果を読み戻しても `tool_use_id` が残る**（今の穴の回帰テスト）
- 50 000バイトを超えるツール出力が、シェル以外のツール（`file_read`）でも切り詰められる
- 切り詰めが二重に掛からない（シェルの既存呼び出しを削り忘れていない）
- `/rpc` セッションはツール呼び出しを永続化しない（既存挙動の回帰）
- ツール呼び出しを含むセッションを保存して読み直すと、
  `tool_use` と `tool_result` が同数・同 id で戻る

## 未解決のまま残すもの

**ツール結果キャッシュに刈り取りが無い。** `DigestCache` と違い、
`ToolResultCache` は何も消さない。1エントリあたりは50 000バイトに縛られるが、
エントリ数は縛られない。今は本番の書き手がいないので溜まっていないが、
**この spec がそれを変える。**

ダイジェストの答え（デイリーログを書いた時点で刈る）は転用できない。ダイジェストは
デイリーログに吸収された時点で役目を終えるが、ツール結果はそのセッションを
開き直すたびに要る。期限はずっと長く、正しい信号が何かは別に考える必要がある。

[#193](https://github.com/fluo10/sapphire-agent/issues/193) に切り出した。
この spec の実装より前に片付ける必要は無い — キャッシュミスは
`MISSING_RESULT` に縮退し、対は保たれるので、刈り取りが遅れて入っても壊れない。

## 実装時の訂正

### 拒否理由は `ToolSet::execute` を通らない

決定1は「組み込みツールも MCP ツールも、拒否されたときの理由文字列も、すべて
`ToolOutput` としてそこを通る」と書いたが、拒否理由は通らない。
`src/serve/mod.rs` と `src/agent.rs` が
`results.push((id, ToolOutput::from(reason)))` で直接組み立てている。

実害は無い — 理由は `policy::refusal_message` の定型文で構造上短い。ただし
「全部がそこを通る」という前提で後から何かを足すと外れるので、
`ToolSet::execute` の doc コメントに但し書きを残した。

### 上限は全トランスポートに掛かる

`ToolSet::execute` は `src/agent.rs` からも呼ばれるので、50 000バイトの上限は
Matrix と Discord のツール結果にも掛かる。spec は ACP の文脈で書いていたが、
合流点が共有されている以上、片方だけ縛る理由が無い。意図した結果である。

### `truncate_output` は冪等ではなかった

spec は「シェルの既存の呼び出しは削る — 二重に掛けると省略マーカーが入れ子になる」
と書いた。正しいが、原因は呼び出しの重複ではなく関数そのものにあった。

旧定数は head 20 000 + tail 30 000 で、そこに省略マーカーが**上乗せ**されるため、
出力が上限の 50 000 を約35バイト超える。つまり切り詰め済みの結果をもう一度通すと
また切られる。呼び出しが1箇所しかなかったので露見していなかっただけ。

head・tail・マーカーの予算が合計で上限に収まるように定数を組み直し、
「一度切った結果をもう一度通しても変わらない」ことをテストで固定した。
上限は上限であるべきで、それは呼び出し側の規律ではなく関数の性質であるほうがよい。

### `sha256: null` は実際には出ない

決定3は `StoredPart::ToolResultRef` の JSON 表現を次のように書いた:

```jsonc
{"tool_result_ref": {"tool_use_id": "c1", "sha256": "ab12…"}}   // 内容あり
{"tool_result_ref": {"tool_use_id": "c1", "sha256": null}}       // 内容なし
```

実装は `sha256` に `#[serde(skip_serializing_if = "Option::is_none")]` を付けている
（`#[serde(default, ...)]` と対で、旧形式の裸文字列の読み込みも保てるようにするため）。
`None` はフィールドごと省略される。「内容なし」の実際の表現は次の通り:

```jsonc
{"tool_result_ref": {"tool_use_id": "c1"}}                       // 内容なし
```

読み手側（`load_part`）は `sha256` の有無に関わらず同じ扱いなので挙動に影響は無い。
ドキュメント上の表記の誤りだけの訂正。
