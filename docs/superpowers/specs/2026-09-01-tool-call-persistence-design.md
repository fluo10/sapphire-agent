# ツール呼び出しを永続化し、ターン間はメモリから追い出す

- **対象**: `src/serve/mod.rs`（`run_llm_turn`）、`src/acp_session.rs`、
  `src/provider/mod.rs`、`src/tools/builtin_tools.rs`
- **イシュー**: [#191](https://github.com/fluo10/sapphire-agent/issues/191)
- **前提**: ACP ストア分離（PR #188）がマージ済み、または同じブランチ上

## なぜ

理由は2つあり、後者のほうが重い。

**再読み込みで「何をしたか」が失われる。** ACP セッションを開き直すと、話した内容は
戻るが、エージェントがどのファイルを読み、どのテストを走らせ、何を編集したかは
残っていない。`run_llm_turn` は `tool_use` と `tool_result` をどのトランスポートでも
捨てているので、復元された履歴は API 的には妥当だが薄い。ストア分離の spec は
これを決定4で明示していたのに、実装計画がタスクを持たなかった。結果として
`ToolResultCache` は本番の呼び出し元を持たないまま出荷されている。

**ツール結果がメモリに残り続ける。** `state.sessions` は一度も掃除されず、
`remove` も `retain` も無い。プロセスが起動中に開いたセッションは、全履歴を
抱えたまま残る。そしてツール結果には上限が無い — `truncate_output`（50 000字）は
シェルの stdout/stderr にしか掛かっておらず、`file_read` は読んだファイルを
まるごと履歴に載せる。エージェントが1日読んだもの全部が常駐する。

**まだ観測はされていない。** これは理屈上の圧力であって、測った結果ではない。
だからこの spec は投機的な作り込みをしない — 永続化という機能上の穴を塞ぎ、
**そこに乗るだけの、ほぼ費用ゼロのメモリ対策だけ**を同梱する。

## やらないこと

**アイドルセッションの `state.sessions` からの破棄はしない。** おそらく一番効く手で、
ストア分離によって初めて安全になった（以前は捨てると会話が消えた）。しかし新しい
方針が要る — いつ捨てるか、進行中のターンをどう扱うか、開き直しにいくらかかるか。
観測がない段階でそれを決めるのは投機。**代わりに測れるようにする**（後述）。

**replay でツール呼び出しをエディタに出すのもしない。**
[#192](https://github.com/fluo10/sapphire-agent/issues/192) に切り出した。動機は
メモリであって、replay の描画は直交する。ただし非対称は残る: モデルは全履歴を
見るのに、開き直したスレッドではツール呼び出しの箇所が空く。今と同じ状態が続くだけで、
悪化はしない。

**既存4ストア（`cross-device` / `channel` / `device-default` / `mcp`）は変えない。**
それらの行形式に `ToolResultRef` は無く、変換する理由も無い。永続化は ACP セッションだけ。

## 決めたこと

### 1. ツール出力の上限を全ツールに掛ける

`truncate_output`（50 000字、先頭20 000 + 末尾30 000、間に省略マーカー）は今
シェルの stdout/stderr にしか掛かっていない。**これを `ToolSet::execute`
（`src/tools/mod.rs:125`）に移し、全ツールの結果に掛ける。**

そこが唯一の合流点である。組み込みツールも MCP ツールも、拒否されたときの
理由文字列も、すべて `ToolOutput` としてそこを通る。ツールごとに掛けると
新しいツールが追加されるたびに掛け忘れが起きる。

シェル側の既存の呼び出しは削る — 二重に掛けると省略マーカーが入れ子になる。

理由は3つ。ライブと再読み込みで見えるものが一致する。キャッシュとディスクの
成長が縛られる。ハイドレートで実体化する量が縛られる。

そして既存の不整合が消える — なぜシェルだけ切って `file_read` は切らないのか、
という問いに答えが無かった。

**代案を却下した理由。** 「無制限のままキャッシュを年齢で刈る」も考えたが、
同一セッション内でターン N とターン N+1 でモデルの見えるものが変わり得る:
N では実体、N+1 では参照からの復元で、その間に刈られていれば
プレースホルダになる。**モデルへの入力が静かに変わるのは避ける。**

上限を掛けた結果は切り捨て済みのものが唯一の真実になるので、この問題は起きない。

### 2. ACP セッションの `tool_use` / `tool_result` を永続化する

`run_llm_turn` の2箇所、今「意図的に永続化しない」とコメントされている地点で、
`is_acp` のときだけストアに追記する。

- `tool_use` を持つアシスタントメッセージ（`src/serve/mod.rs:2230` 付近）
- ツール結果のメッセージ（`src/serve/mod.rs:2336` 付近）

ストア側は既にある。`store_part` は `ContentPart::ToolUse` を
`StoredPart::ToolUse` に、`ContentPart::ToolResult` をキャッシュ書き込み +
`StoredPart::ToolResultRef` に変換する。

### 3. キャッシュ不在時に対を壊さない

現状の穴: キャッシュが無いと `store_part` は `StoredPart::Other` を書き、
`tool_use_id` を落とす。`load_part` はそれをただのテキストマーカーとして読み戻すので、
**`tool_use` に対応する `tool_result` が無い履歴ができ、API がそれを拒否する。**
書き込み側のミスは、読み出し側のミスと違って対を保てていない。

`StoredPart::ToolResultRef` の `sha256` を `Option<String>` にする。

```jsonc
{"tool_result_ref": {"tool_use_id": "c1", "sha256": "ab12…"}}   // 内容あり
{"tool_result_ref": {"tool_use_id": "c1", "sha256": null}}       // 内容なし
```

`None` は「ここに結果があったことは分かるが、中身は持っていない」。`load_part` は
どちらの場合も `ContentPart::ToolResult` を作り、内容はキャッシュから、
取れなければ `MISSING_RESULT` を入れる。**`tool_use_id` はどちらの経路でも保たれる。**

これは書き込み時にキャッシュが無い場合と、書けたが後で消えた場合を、読み手にとって
同じ形にする。読み手が区別する理由は無い — どちらも「対はある、中身は無い」。

### 4. ターン間はメモリから追い出す

`ContentPart::ToolResultRef { tool_use_id, sha256 }` を足す。フックは2箇所とも既にある。

- **scrub**（`src/serve/mod.rs:2346`、`image_cache::scrub_history_inplace` の隣）:
  ターンが終わった履歴の `ToolResult` を、キャッシュに書いたうえで参照に置き換えてから
  `state.sessions` に格納する。
- **hydrate**（`:2193`、`image_cache::hydrate_history` の隣）: プロバイダ呼び出しの
  直前に参照をキャッシュから実体に戻す。取れなければ `MISSING_RESULT`。

**画像とは向きが逆である。** `image_cache::hydrate_history` は `ImageRef` を
テキストマーカーに*格下げ*する — 過去の画像をモデルに再送して再課金しないため。
ツール結果は会話の一部であり、モデルが毎ターン必要とするので、まるごと復元する。
同じ2つのフックに、目的の違う2つの規則が同居することになるので、両方に理由を書く。

**効くのはターンとターンの間だけ。** プロバイダ呼び出しの瞬間は
`history_for_provider` が全部を実体化するので、ピークは減らない。減るのは常駐分で、
アイドルセッションが何本もぶら下がるときに効く。この限界は spec に書いておく —
「参照化したからメモリ問題は解決した」と後で誤読されないように。

**キャッシュが無ければ scrub は何もしない。** `image_cache::scrub_history_inplace` が
`cache` が `None` のとき即 return するのと同じ。参照に置き換えてから復元できないのは、
内容を捨てるのと同じなので。

### 5. 測れるようにする

破棄を投機で入れない代わりに、次に決めるときの材料を出す。

`state.sessions` の常駐量を定期的にログに出す: セッション数、メッセージ総数、
`ContentPart::Text` と `ToolResult` の合計バイト数。既存の30分ダイジェスト掃き出しの
タスクに相乗りさせる（別のタイマーを増やさない）。`debug` レベル。

これで「多数のセッションが溜まる」のか「1本が長く伸びる」のかが、推測ではなく
記録から分かる。

## データフロー

```
ツール実行
  → truncate_output（全ツール、50 000字）
  → ContentPart::ToolResult  ← ライブのターンはこれを見る
       ↓ ターン終了
     scrub: キャッシュに書く → ContentPart::ToolResultRef を state.sessions へ
     store: StoredPart::ToolResultRef を JSONL へ（sha256 は Option）
       ↓ 次のターン
     hydrate: キャッシュから読む → ContentPart::ToolResult
       （ミス時は MISSING_RESULT、tool_use_id は保たれる）
```

再読み込み時は `history()` が JSONL から同じ `ContentPart::ToolResult` を組み立てる。
ライブの継続と再読み込みが同じ形に収束する。

## エラー処理

- **キャッシュ書き込み失敗**: 警告し、内容を残したまま先へ進む
  （`image_cache::scrub_history_inplace` と同じ）。メモリは減らないが、会話は壊れない。
- **キャッシュ読み出しミス**: `MISSING_RESULT`。対は保たれ、モデルは必要なら
  ツールを呼び直せる。
- **ストア追記失敗**: 警告して続行。今の挙動と同じ。ターンは進み、
  次の再読み込みでその部分が欠ける。
- **キャッシュ自体が開けない**: 両方の経路が縮退する。永続化は
  `sha256: None` を書き、scrub は何もしない。

## テスト

- ツール結果が JSONL に参照として書かれ、内容は JSONL に現れない（既存テストの拡張）
- `tool_use` と `tool_result` の対が、キャッシュを消しても保たれる
- **キャッシュ不在で書いた結果を読み戻しても `tool_use_id` が残る**（今の穴の回帰テスト）
- scrub 後の `state.sessions` に生のツール結果内容が残っていない
- hydrate がキャッシュから内容を戻し、ミス時は `MISSING_RESULT` を入れる
- 50 000字を超えるツール出力が、シェル以外のツールでも切り詰められる
- `/rpc` セッションはツール呼び出しを永続化しない（既存挙動の回帰）

## 未解決のまま残すもの

**ツール結果キャッシュに刈り取りが無い。** `DigestCache` と違い、
`ToolResultCache` は何も消さない。1エントリあたりは50 000字に縛られるが、
エントリ数は縛られない。今は本番の書き手がいないので溜まっていないが、
**この spec がそれを変える。**

ダイジェストの答え（デイリーログを書いた時点で刈る）は転用できない。ダイジェストは
デイリーログに吸収された時点で役目を終えるが、ツール結果はそのセッションを
開き直すたびに要る。期限はずっと長く、正しい信号が何かは別に考える必要がある。

[#193](https://github.com/fluo10/sapphire-agent/issues/193) に切り出した。
この spec の実装より前に片付ける必要は無い — キャッシュミスは
`MISSING_RESULT` に縮退し、対は保たれるので、刈り取りが遅れて入っても壊れない。
