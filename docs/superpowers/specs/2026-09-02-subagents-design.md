# サブエージェントに仕事を委譲する

- **対象**: `src/serve/mod.rs`（`run_llm_turn` のツールループ抽出）、`src/tools/`（新規）、
  `src/agents.rs`（新規）
- **前提**: ACP のクライアント側ツール（#198）がマージ済み

## なぜ

理由は2つあり、どちらも「速くする」ではない。

**メインエージェントのプロンプトには、開発に要らないものが意図的に入っている。**
`SOUL.md`・`IDENTITY.md`・`USER.md` が注入され、メモリと今日の横断ダイジェストが載る。
それは**そうあってほしいから**そうなっている — 一緒に開発する相手であって、
道具ではない。しかしコードレビューを頼むときに昨日の雑談は要らない。
**サブエージェントは、その要らない部分を落とす手段である。**

**大きな調査が親の履歴を膨らませる。** 30ファイル読んで結論が3行なら、
親に残るべきは3行である。今は30ファイル分が全部残り、以降のターンで毎回モデルに送られる。

**並列実行と別モデルは目的ではない。** llama.cpp を1スロットで動かすなら並列は
そもそも効かないし、モデルの使い分けは今回求められていない。それらを設計に
含めないことで、同時実行の仕組みが丸ごと不要になる。

## 決めたこと

### 1. 定義は `<workspace>/agents/<name>.md`

`<workspace>/heartbeat/*.md` と同じ形。**新しい規約を作らない。**

```markdown
---
description: コードレビュー。差分を読んで問題を報告する。編集はしない。
tools: [client_file_read, workspace_search, retrieve]
---
あなたはレビュアーです。…
```

- **`description`**: 親のモデルが「これに投げるか」を判断する**唯一の材料**。
  ここが弱いと、そのエージェントは呼ばれない。
- **`tools`**: 省略可。省略時は**親に見えているツールから `subagent` を除いたもの**。
- **本文**: サブエージェントのシステムプロンプト。**これで全部である**（次項）。

読み込みは `heartbeat_config::load` と同じ — ディレクトリを走査し、
フロントマターが無い/壊れているファイルは警告して飛ばす。**1つ壊れていても
他は動く**のが既存の流儀で、それに合わせる。

### 2. ワークスペースのシステムプロンプトは継承しない

サブエージェントのシステムプロンプトは**定義の本文だけ**。

継承しないものを名指しする — `Workspace::build_system_prompt` が積むもののうち:

- `AGENTS.md` / `SOUL.md` / `IDENTITY.md` / `USER.md` / `TOOLS.md` の注入
- メモリ
- 今日の横断ダイジェスト
- 部屋のメタデータ
- 設定の `anthropic.system_prompt`

**これを落とせることが、この機能を作る理由の1つである。** 継承を既定にすると
目的に逆行する。

日時だけは例外として渡す — 「今日の日付」を知らないエージェントは
`memory_add` のような日付を書くツールを正しく使えず、これは人格ではなく事実である。

**プロジェクトの規約は別問題である。** クライアント側プロジェクトの `CLAUDE.md` は
*共有すべき*もの — 人格ではなく、編集している対象リポジトリの規則だから。
ただし**メインエージェントも今それを読んでいない**ので、
[#199](https://github.com/fluo10/sapphire-agent/issues/199) で両方まとめて扱う。
この spec の範囲外だが、入ったときにサブエージェントにも渡る形にしておく。

### 3. ツールは `subagent` 1つ

```json
{"agent": "reviewer", "prompt": "この差分をレビューして"}
```

エージェントごとにツールを生やさない。ツール一覧が定義の数だけ伸びるのを避け、
説明を1箇所に集める。**利用可能なエージェントとその `description` は
`subagent` の説明文に列挙する** — 親が選ぶのに必要な情報はそこに全部ある。

`ToolKind` は `Other`。実際に何をするかは委譲先次第で、`Read` とも `Execute` とも
言えない。`Other` は最も厳しいバケットで、分類できないものが安全側に倒れる。

**帰結を明示しておく。** ポリシー表は `Other` を「risky」に分類しており、
`Origin::Channel` は risky を無条件に拒否する。したがって
**Matrix と Discord からはサブエージェントを呼べない。** 実質 ACP 専用の機能になる。

必要以上に厳しい — サブエージェントは親と同じゲートを通るので、channel から
呼べても channel が許すことしかできない。しかし目的が開発作業である以上、
そこを緩めるのは今回得るものが無く、**分類が「分からないものは断る」と
言っているのに例外を作るほうが筋が悪い。** 必要になったら、そのときに
理由と一緒に開ければよい。

定義はプロセス起動時に読む。エージェントを足したら再起動が要る —
heartbeat タスクと同じで、v1 ではそれでよい。

### 4. 親の `TurnHost` をそのまま渡す

サブエージェントのツール呼び出しは、**親と同じゲートを、同じ `Origin` で、
同じクライアントに対して**通る。

これは選択肢ではない。別扱いにすれば「サブエージェントに頼む」が承認の
迂回路になり、親が断られたことを委譲経由で実行できてしまう。

**承認要求は普通にユーザーへ出る。** サブエージェントの作業が見えなくなるより、
問い合わせが増えるほうがましである。`Read` は既定で自動許可なので、
調査系エージェントなら実際にはほとんど聞かれない。

副次的な利点として、**サブエージェントは `ToolSet::execute` の中で走る** —
そこは既に `scope_acp_client` と `scope_timer_origin` の内側なので、
クライアント側ツールが**何もしなくても動く**。親のターンが取り消されれば
サブエージェントの future も一緒に落ちる。

### 5. 再帰は深さ1

`subagent` をサブエージェントのツール一覧に**入れない**。定義の `tools` に
書かれていても除く。

深さの上限を設けるより単純で、深さ2以上に用途が思いつかない。
必要になったら、そのとき上限付きで開ければよい。

### 6. 内部履歴は永続化しない

サブエージェントの履歴は、その呼び出しの間だけメモリに存在する。

親のセッションに残るのは `subagent` の**ツール呼び出しとその結果**だけで、
これは既存のツール呼び出し永続化（#191）がそのまま拾う。再読み込みすると
「Xを委譲してYが返った」が見える — **コンテキスト隔離の意味そのもの**である。

ツール呼び出しを永続化しているのは ACP セッションだけなので
（既存4ストアは [#194](https://github.com/fluo10/sapphire-agent/issues/194) 待ち）、
それ以外のトランスポートでは委譲の記録も残らない。前項のとおり
サブエージェント自体が実質 ACP 専用なので、今のところ食い違いは起きない。

### 7. ツールループを抽出する

`run_llm_turn` のツールループ（`src/serve/mod.rs:2365-2634`、約270行）を、
セッション永続化から切り離して再利用可能にする。そこには許可ゲート・圧縮・
画像ハイドレート・ツール結果永続化が全部入っており、**複製すれば
サブエージェント側だけ直し忘れる未来が確定する。**

抽出後の関数が受け取るもの: 履歴、システムプロンプト、ツール仕様、プロバイダ、
`TurnHost`、そして「永続化するか」。`run_llm_turn` はそれを永続化ありで呼び、
`subagent` ツールは永続化なしで呼ぶ。

**これがこの spec で一番危険な部分である。** 4つのトランスポート
（ACP・`/rpc`・`/a2a`・音声）と channel が通る hot path で、壊れれば全部に効く。
実装計画では**抽出だけを独立したタスクにし、挙動が1ビットも変わらないことを
既存テストで確かめてから**、サブエージェントを足す。

## データフロー

```
親のモデルが subagent{agent: "reviewer", prompt: "…"} を呼ぶ
  → 許可ゲート（Other → 親の Origin の判断表）
  → 定義を引く。無ければエラーをツール結果に返す（ターンは続く）
  → 新しい履歴 = [user: prompt]
     システムプロンプト = 定義の本文 + 日時
     ツール = 定義の tools（省略時は親の可視集合）から subagent を除く
     プロバイダ = 親と同じ
     TurnHost = 親のもの
  → 抽出したツールループを、永続化なしで回す
  → 最終テキストをツール結果として親に返す
     内部履歴は捨てる
```

## エラー処理

- **定義が見つからない**: ツール結果にエラーを返し、利用可能な名前を列挙する。
  ターンは続く — 親が選び直せる。
- **定義のフロントマターが壊れている**: 起動時に警告して、その1つを飛ばす。
  他のエージェントは使える。
- **`tools` に存在しないツール名がある**: 起動時に警告し、その名前を落とす。
  定義ごと無効にはしない — タイプミス1つでエージェントが消えるほうが困る。
- **サブエージェントが `MAX_TOOL_ROUNDS` を使い切った**: そこまでの出力を
  「予算切れ」の旨とともに親へ返す。親が続きを頼むか諦めるかを決める。
- **サブエージェントのプロバイダ呼び出しが失敗**: エラーをツール結果に返す。
  親のターンは落とさない。
- **`tools` が空**: 定義として有効。ツールを持たないエージェントは、
  与えられたプロンプトだけで考えて答える — 要約や判断には十分ありうる。

## テスト

- 定義がフロントマターと本文に分かれて読まれ、壊れた1つが他を巻き込まない
- **サブエージェントのシステムプロンプトにワークスペースのファイルが入っていない** —
  `SOUL.md` を置いた状態で確かめる（この機能の主目的の回帰テスト）
- サブエージェントのツール一覧に `subagent` が無い — 定義の `tools` に
  書いてあっても
- 定義の `tools` が空/省略のそれぞれで、期待どおりのツール集合になる
- **サブエージェントのツール呼び出しが親と同じ `Origin` でゲートを通る** —
  親が `Origin::Channel` のとき、サブエージェントから `Execute` が拒否される
- 存在しないエージェント名がエラーとして返り、ターンが続く
- サブエージェントの内部履歴が親の履歴にもストアにも現れない
- 親のツール呼び出しと結果は従来どおり永続化される
- **抽出の前後で `run_llm_turn` の挙動が変わらない**（既存テスト全体）

## やらないこと

- **並列実行**。求められておらず、llama.cpp を1スロットで動かすなら効かない。
  同時実行の仕組みを持ち込まないことで、設計が丸ごと単純になる。
- **エージェントごとのモデル選択**。今回の目的に含まれない。プロバイダは親と同じ。
- **深さ2以上の入れ子**。用途が思いつかない。
- **定義のホットリロード**。起動時に読む。heartbeat タスクと同じ。
- **プロジェクト規約の読み込み**。[#199](https://github.com/fluo10/sapphire-agent/issues/199)。
  そちらが入ればサブエージェントにも渡すが、この spec では扱わない。

## 実装時の訂正

- **「深さは構成で決まる」は誤りだった。** 「5. 再帰は深さ1」は、
  `subagent` をサブエージェントの `tool_specs` に含めなければそれで
  上限は保証されると書いていたが、`ToolSet::execute` は共有 `ToolSet` に
  登録された全ツールを名前でディスパッチするため、`tool_specs` に無い
  名前を呼んでも実際には実行できてしまっていた。`TurnLoop::run` に
  「その回の `tool_specs` に無い名前は拒否する」ゲート
  （`Refusal::NotOffered`）を追加して初めて、深さ1の上限・定義の
  `tools:` 制限・親の経路での同種の穴が閉じた。三つとも同じ穴の
  同じ修正であって、別々の対応ではない。
- **決定6の「親のセッションに記録が残る」は ACP セッションに限った話だった。**
  本文は前提を明示していなかったが、ツール呼び出しの永続化自体が
  ACP セッションのみ（既存4ストアは #194 待ち）なので、この決定が
  効くのも ACP セッションだけである。README にもその前提を明記した。
- 上記以外に、実装が spec の決定事項そのものと食い違った箇所は無い。
