# ACP セッションを自前のストアに分ける

- 日付: 2026-08-31
- 対象: `src/session.rs`, `src/serve/acp.rs`, `src/serve/mod.rs`,
  `src/agent.rs`, `src/periodic_log.rs`, 新規: ツール結果キャッシュ
- 訂正する設計: `2026-08-31-acp-session-load-design.md`
- **同じブランチの上に積む。** 訂正対象の設計はまだマージされていないので、
  「機能を入れてから直す」ではなく、一つの PR (#188) が最終的に
  「ACP に自前のストアを与え、Zed から過去のセッションを開けるようにする」
  という一貫した変更になる。先行するコミットは個別にレビュー済みなので
  書き換えず、その上に載せ替えを積む。
- 前提: `2026-08-30-acp-permissions-design.md`

## 背景

ACP セッションと `/rpc` セッションは、いま**同じストア・同じ形式**を共有している。
そう決めたのは「別に定義を用意するのは冗長」という理由だったが、二つの点で
間違っていた。

**体験として混ざるのが不自然。** Zed のスレッド一覧に、Matrix の会話も
`/rpc` の呼び出しも並ぶ。別のものが同じ場所に出ている。

**規格として乖離していく。** `/rpc` はこちらの目的のために自分で決めた形式で、
ACP は外部で定義され今後改定される規格。同じ形に押し込め続ける理由がない。

そして**乖離は既に始まっている**。この分岐を書いている時点で:

- `run_llm_turn` は `ensure_session(.., "rpc", ..)` をハードコードしている。
  **ACP セッションは `channel: "rpc"` として記録され、grain-id まで振られる。**
  ディレクトリは `cross-device/`（`cross_device_session_store` の kind）なので、
  メタデータの `channel` と実際の置き場所すら食い違っている。
- `SessionMeta` の Option フィールドは5つあり、それぞれ実質1つのトランスポート
  しか使わない: `public_id`（API）、`project`（MCP）、`device_id` と
  `room_profile`（voice）、そして `cwd`（ACP）。構造体はトランスポートごとの
  形の和集合になっている。
- `SessionInfo.cwd` は ACP が「必須かつ絶対パス」と決めているが、こちらの
  メタデータは `Option`。その差を埋めるためだけに「cwd が無ければワークスペース
  root を報告する」というフォールバックが存在する。あれは修正ではなく症状。
- **`SummaryLine` はストアによって意味が違う。** MCP ストアでは
  `recall_memory` が `project_summary` として読む意味的コンテンツだが、
  rpc/ACP ストアでは再開用のキャッシュ。同じ形が置き場所で別物になっている。

## 決めたこと

1. **ACP セッションを `<sessions_dir>/<namespace>/acp/` に分ける。** ディレクトリ
   走査などの機構は共有し、**行の形式だけを新しい型が所有する**。
2. **イベントに UUIDv7 の `id` と `parent` を持たせる。** 後から埋め戻せないので
   今入れる。
3. **1イベント1ファイルにはしない。** 今回は1セッション1ファイルのまま。
4. **ツール結果をワークスペース外のキャッシュに置き、JSONL には参照を入れる。**
5. **再開用の要約を廃止する。**
6. **移行しない。** 既存の4ストアは形式もコードもそのまま。

### 2 と 3 — 不可逆な部分だけを今やる

高価で後戻りできないのは**ファイル配置ではなくイベントの同一性**。
「どのイベントがどれの後に続くか」は後から復元できないが、`id` と `parent` さえ
あれば、1イベント1ファイルへの分割は「行をファイルに移す」機械的な操作になる。

1イベント1ファイルが要るのは remote-workspace の同期を実装するときで、それは
オフライン利用という**まだ確定していない需要**に依存している。分割すると1セッション
の読み込みが複数ファイルの読み出しになり、キャッシュ DB が要る。投機的に払う
必要はない。

### 5 — 再開用要約が要らなくなる理由

当初は「キャッシュから復元できない場合に限り要約を作る」と考えていた。しかし
**ツール結果が失われていても、`tool_result` にプレースホルダを入れれば API 的に
妥当な履歴が復元でき、会話の構造も保たれる**。モデルは必要なら同じツールを
呼び直せる。

対して要約は、モデル呼び出しのコストを払った上でターン構造ごと失う。
プレースホルダのほうが安く、忠実。したがって再開用要約という概念自体が不要。

**ターン中の `maybe_compress` は残す。** あれはコンテキスト窓が溢れそうなときの
管理で、再開とは別の仕事。

## ストアの配置

```
<sessions_dir>/<namespace>/acp/<uuid>.jsonl             ← 新設
<sessions_dir>/<namespace>/cross-device/<uuid>.jsonl    ← 従来。/rpc と、今の ACP
<sessions_dir>/<namespace>/channel/<uuid>.jsonl         ← Matrix / Discord
<sessions_dir>/<namespace>/device-default/<uuid>.jsonl  ← voice / heartbeat
<sessions_dir>/<namespace>/mcp/<uuid>.jsonl             ← MCP レポート
```

**新設は `acp/` の1つだけで、既存の4つは一切触らない。** 本番のストアが4種類
あることは、この分離が例外ではなく既定の作法であることも示している —
トランスポートごとにストアを分ける仕組みは既にあり、ACP だけがそこに乗り
損ねていた。

`collect_session_files(base_dir, kind)` は `kind` でディレクトリを分ける既存の
仕組みなので、走査はそのまま使える。所有するのは行の形式だけ。

`run_llm_turn` の `ensure_session(.., "rpc", ..)` ハードコードを、セッションの
出自で分岐させる。`channel: "rpc"` という嘘が消える。

## イベント形式

現在の行は「どのフィールドがあるか」で種類を見分けている（`MetaLine` は `meta`
を持つ、等）。新形式は**タグ付き**にする。

```jsonc
// ヘッダ。1行目。id も parent も持たない
{"header": {
  "session_id": "01912...",
  "namespace": "default",
  "cwd": "/home/u/project",
  "created_at": "2026-08-31T09:00:00Z"
}}

// イベント
{"id":"01912...","parent":null,       "at":"...","kind":"message","role":"user","parts":[...]}
{"id":"01912...","parent":"01912...","at":"...","kind":"message","role":"assistant","parts":[...]}
{"id":"01912...","parent":"01912...","at":"...","kind":"title","title":"..."}
{"id":"01912...","parent":"01912...","at":"...","kind":"closed"}
```

**`cwd` はヘッダの必須フィールド。** ACP セッションは必ず `session/new` か
`session/load` から cwd を受け取るので、`Option` である理由がない。これにより
`Workspace::root()` フォールバックと、cwd を持たないセッションを一覧に出す分岐が
**両方とも不要になる**。

### `parent` の意味と規則

- **`parent: null` は「セッション最初のイベント」。** ヘッダを根イベントにする
  特別扱いを避ける。
- **`parent` は「書き手が追記した時点で末尾だと認識していたイベント」。** これが
  オフラインの分岐を検出可能にする。
- **単数。** 木で十分 — 分岐の検出が目的で、マージの解決は別問題。同じ `parent`
  を持つイベントが2つあれば分岐。
- **順序の権威は `parent` 鎖であって `id` の時刻ではない。** UUIDv7 は書き手の
  時計を埋め込むので、時計がずれた2台の id は相対順序を誤る。ソートは近似、
  鎖が真実。

### `SummaryLine` は新ストアに存在しない

決めたこと 5 の帰結。行の種類は `message` / `title` / `closed` の3つとヘッダのみ。
`/rpc` と MCP ストアの `SummaryLine` は従来どおり残る。

## ツール結果のキャッシュ

`image_cache` と同型。ワークスペース外、ハッシュアドレス。

```
dirs::cache_dir()/sapphire-agent/tool-results/<sha256>
```

JSONL 側は参照だけ:

```jsonc
{"kind":"message","role":"assistant","parts":[
  {"tool_use":{"id":"c1","name":"file_read","input":{"path":"src/main.rs"}}}]}
{"kind":"message","role":"user","parts":[
  {"tool_result_ref":{"tool_use_id":"c1","sha256":"e3b0c442..."}}]}
```

**`tool_use` を持つ assistant メッセージも保存する。** 今は
「tool_use は意図的に保存しない」というコメントとともに捨てているが、対を成せ
なければ復元できない。捨てていた理由は「ファイルを読むたびにワークスペースが
太る」ことで、それは結果をキャッシュに追い出すことで解決する。

### キャッシュミス

`tool_result` の中身を次の文言に置き換える:

```
[この tool_result はもう保存されていません。必要なら同じツールを呼び直してください]
```

`tool_use` と `tool_result` の対応は保たれるので**履歴は API 的に妥当なまま**。
モデルは必要なら呼び直せる。要約を作る必要はない。

## サマリーとダイジェスト

どちらもワークスペース外へ。同期されなくなり、別端末では再生成になる。
ローカルモデルなら再生成は安い。

- **再開用サマリー: 廃止。** 削除するのは `serve/mod.rs` の
  `summarize_all_sessions` — doc コメントが目的をそのまま述べている:
  「次のプロセスが生の履歴を再生せずに文脈を回復できるよう、すべての
  in-memory API セッションを要約して `SummaryLine` を追記する」。これが
  ACP と `/rpc` の再開用要約であり、キャッシュからの復元が置き換える対象。

  **`src/agent.rs` の3箇所（`:211` 定期、`:257` shutdown、`:653` 日境界）は
  触らない。** あれは `channel` ストア — Matrix と Discord の会話 — に書いており、
  この spec の対象外。同名の仕組みが別のストアに二つあるのは、まさにこの
  分離が正そうとしている混同の一例。
- **ダイジェスト: キャッシュに永続化。** インメモリ再生成も検討したが、起動時に
  複数セッション分の要約が走るのは重い。

### ダイジェストの有効期間

`intraday_digests_for_day` の呼び出しは `periodic_log.rs:1179-1184` の3箇所だけで、
**すべて `today`**。ダイジェストは今日の分しか読まれない。日境界を越えて
デイリーログが生成されれば役目を終える — デイリーログはワークスペース内に残り、
検索対象であり続ける。

したがって**キャッシュが失われても損失は「今日のダイジェスト」だけ**で、
全履歴の再生成ではない。`cache_dir` で構わない。

**デイリーログを書いた時点で、それより前のダイジェストを削除する。** 今は何も
消しておらず無限に溜まっている。

## 読み込み

```
ヘッダを読む
  → イベントを parent 鎖で辿る
  → tool_result_ref をキャッシュから hydrate
  → 見つからないものはプレースホルダに置換
```

分岐（同じ `parent` を持つイベントが複数）を見つけたら、**警告を出して
`at` の新しいほうを辿る**。マージはしない。今は分岐が起きる経路がない
(remote-workspace 未実装) ので、これは将来のための検出であって解決ではない。

## ACP アダプタ側

`session/list` と `session/load` が新ストアだけを見る。**`/rpc` セッションは
Zed の一覧に出なくなる** — この spec の動機そのもの。

**ハンドラ本体はほぼそのまま残る。** namespace 境界、区別できない拒否文言、
replay の順序、adopt の手順、接続カウンタ — どれも「どのストアを読むか」に
依存しない。変わるのは呼ぶストア型だけ。既に何周ものレビューで固めた
セキュリティ境界のテストも、ストアの構築だけ差し替えれば通る。

このブランチの先行コミットで入れた次のものは不要になり、削除する:

- `SessionMeta.cwd`（新ストアではヘッダの必須フィールド）
- `Workspace::root()` と、それを使う cwd フォールバック、およびそのテスト
- `pending_cwd`（ヘッダをセッション作成時に書くので、初回ターンまで持ち回る
  必要がない）
- `session_header()` / `list_session_headers()`（新ストアが自前の読み口を持つ）

## 移行しない

既存の4ストアは形式もコードもそのまま。このブランチ以前に作られた ACP セッションは
`cross-device/` に残り、新ストアからは見えなくなる。

失われるのは「Zed の一覧に過去の ACP セッションが出ること」だけ。中身は
デイリーログに含まれ、retrieve で検索できる。旧フォーマットの読み手は残るので、
ファイルが無駄になるわけでもない。

セッション単位の復元が効かなくなるだけで、その代償を払う価値はある — 移行
コードは書かれ、テストされ、一度しか使われず、その後も永久に残る。

## テスト

- 新ストアの往復: ヘッダ + `message` / `title` / `closed`
- `parent` 鎖が追記順を保つ
- **分岐の検出**: 同じ `parent` を持つ2イベントを手で書き、警告と `at` による
  選択を確認
- **`parent: null` が最初のイベントにだけ現れる**
- ツール結果のキャッシュ往復
- **キャッシュミス時にプレースホルダで API 妥当な履歴になる** — `tool_use` の
  数と `tool_result` の数が一致すること
- `session/list` が `/rpc` セッションを返さない
- ダイジェストがデイリーログ生成時に刈られる
- **回帰: 既存4ストア（cross-device / channel / device-default / mcp）の
  読み書きが一切変わっていない**
- 回帰: 再開用要約の削除後も `maybe_compress` が動く

## 別イシューに切り出すもの

- **1イベント1ファイルとキャッシュ DB。** remote-workspace を実装すると決めた
  ときに。`id` と `parent` があるので機械的な操作になる。sapphire-journal の
  rusqlite と、エージェント自身の retrieve DB という前例が2つある。
- **セッション単位のロック。** 並行ターンの履歴レース（このブランチで警告だけ入れた）。
- **`session/close` と `session/delete`。**
- **`SessionMeta` の残りの Option フィールド。** `public_id` / `project` /
  `device_id` / `room_profile` も、それぞれ1つのトランスポートしか使わない。
  ACP を分けた後、同じ問いが MCP と voice にも立つ。
